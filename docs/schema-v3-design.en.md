# Database Schema v3: A Relational Model Without the Compatibility Layer

Status: **Approved, in progress** (2026-10-09). This is the English version; the Chinese original [schema-v3-design.md](schema-v3-design.md) and the Japanese version [schema-v3-design.ja.md](schema-v3-design.ja.md) have the same content and are maintained together. The appendix of all three is generated by a script from the same SQL.

**[server/v3/schema.sql](../server/v3/schema.sql) is the authoritative column list**: every table and every column (including `rid`, `user_id`, `position`, timestamps, foreign keys, constraints and indexes) is listed there with comments, and the schema has been built and verified in SQLite. This document focuses on what each column means, its values and where legacy data comes from. Sample database: `.local/v3-work/sample.sqlite` (contains only knowledge point W5, for reference).

"Legacy source" in the tables tells where a value comes from during migration: `table.column` is a legacy table column; `item_json.xxx`, `settings_json.xxx`, etc. are keys inside JSON columns of legacy tables. Sample data comes from a copy of production data (2026-10-07: 496 knowledge points, 3,048 question rows).

## 1. Why v3

v2 used a set of "mapping specs" to split the legacy JSON into relational tables, then assembled the legacy JSON again with compatibility views so that the old code needed no changes. The price was that the tables were shaped by the legacy JSON rather than by the domain:

- `*_count` and `*_present` columns existed only to tell "missing / empty array / has content" apart, so the legacy JSON could be restored byte for byte.
- `deck` and `wordbook_id` coexisted: built-in decks were inferred, not real wordbooks.
- One concept spelled several ways took several columns: `prompt` / `question_text`, `item_id` / `item_ref`, `tested` / `tested_expression`, `source_draft_id` / `source_draft_ref`.
- The same question was stored once each in knowledge points, drafts, practice sets and snapshots (most of the 3,048 question rows are copies).
- `*_extra` tables held unmodeled fields, and columns such as `item_json_id` existed only for restoration.

v3 decision (confirmed 2026-10-09): **no compatibility with the old API**. The server, MCP and REST read and write the new tables directly, APIs return the new structure, and the Web and iOS data models change with them. Legacy data is migrated directly from the original tables (`legacy_v1_*`, or the original tables in databases not yet migrated), not through the v2 intermediate structure.

## 2. Design principles

1. **Tables follow the domain, with hand-written DDL.** Every column has a business meaning; none exists only to restore an old format.
2. **One concept, one column.** Different spellings in legacy data are merged during migration.
3. **Arrays are child-table rows**, ordered by `position` (from 0). The length is the number of rows and is not stored separately. Missing and empty arrays are not distinguished.
4. **All explanatory text goes into `content_translations`**, one row per language; Japanese source text (examples, prompts, options) is an ordinary column. The "translated fields" of the tables below are not columns of those tables but rows in `content_translations` with `owner_table` = the table, `owner_rid` = the row's `rid` and `field` = the field name. For example, the meaning of knowledge point W5 (rid 347):

   | owner_table | owner_rid | field | language | text |
   |---|---|---|---|---|
   | knowledge_points | 347 | meaning | ja | 物事の全体を、大まかに見渡すこと。 |
   | knowledge_points | 347 | meaning | zh-Hans | 概观、概览 |
   | knowledge_points | 347 | meaning | en | overview, general survey |
5. **Internal primary key `rid` (auto-increment integer)**; externally, the business code `code` (W12, QV15 …, numbered per user and per prefix). Neither legacy string IDs nor legacy codes (IT-000919, etc.) enter the new database: the migration script links old references to new `rid`s with a temporary mapping table that is dropped when migration ends, and writes the mapping to the migration report for checking. Old codes and old links stop working.
6. **Real foreign keys**: child tables use `ON DELETE CASCADE`; cross-entity references (question ↔ knowledge point, practice set ↔ question) use `SET NULL` or forbid deletion according to their delete semantics.
7. **A question is stored once and edited in place, without versions**: practice sets, drafts and knowledge points reference questions through link tables. Options have stable IDs (`question_options.rid`) and the correct answer is marked on the option; clients may shuffle options when presenting a question, and an answer records only the chosen option ID together with the text of the chosen and correct options and whether it was right at the time. Later edits to the question do not change historical correctness or accuracy.
8. **Times** are ISO 8601 text (UTC, with `Z`); **dates** are `YYYY-MM-DD`; **booleans** are 0 / 1.

The body of this document explains the design only; every column of every table (including `rid`, `user_id`, `created_at`, `updated_at`, `position`, foreign keys and constraints) is in the appendix. Tables owned by a user (marked "per user" in their heading) all have `user_id` (owning user, FK → `users`), and their business `code` is numbered per user; child tables belong to a user through their parent and do not repeat `user_id`.

### How multilingual text maps: `languages`, `translatable_fields`, `content_translations`

How the three tables relate:

```
languages (code)                       12 languages
    ▲
    │ language
content_translations ──(owner_table, field)──▶ translatable_fields   which field of which table is translatable (66)
    │ (owner_table, owner_rid)
    ▼
a row of any business table (knowledge_points.rid = 347 …)
```

- **`translatable_fields`** registers every translatable field: `knowledge_points.meaning`, `knowledge_examples.translation`, `question_options.analysis` …, 66 in total; the full list is in section 11 of schema.sql. The "translated fields" listed for each table below are rows of this table.
- **`content_translations`** stores the text itself: one row per language of each field. `(owner_table, field)` must be registered in `translatable_fields` and `language` must exist in `languages`; otherwise the database rejects the write.
- **`owner_table` + `owner_rid`** point to a row of a business table. This cannot be a foreign key (the same column points to dozens of tables), so every business table has a delete trigger: when a business row is deleted, its translations and furigana are deleted too.
- **Language fallback on read**: text is read in the user's explanation language; when missing, the lookup follows `languages.fallback_code` (e.g. ko → en) and finally zh-Hans. The result states which language was actually used and whether it is a fallback.

Example: rows in `content_translations` for knowledge point W5 (`knowledge_points.rid` = 347) and its first example sentence (`knowledge_examples.rid` = 758):

| owner_table | owner_rid | field | language | text | origin | verified |
|---|---|---|---|---|---|---|
| knowledge_points | 347 | meaning | ja | 物事の全体を、大まかに見渡すこと。 | migrated | 1 |
| knowledge_points | 347 | meaning | zh-Hans | 概观、概览 | migrated | 1 |
| knowledge_points | 347 | meaning | en | overview, general survey | ai | 0 |
| knowledge_points | 347 | explanation | zh-Hans | 从整体上把握事物的全貌。 | migrated | 1 |
| knowledge_examples | 758 | translation | zh-Hans | 概览日本经济的历史。 | migrated | 1 |
| knowledge_examples | 758 | translation | en | Survey the history of the Japanese economy. | ai | 0 |

## 5. Wordbooks and knowledge points

### `wordbooks`: wordbooks (per user)

Full columns (including `rid`, `user_id`, timestamps, foreign keys and constraints): appendix [`wordbooks`](#wordbooks).

Unique constraints: `(user_id, code)`, `(user_id, title)`. A wordbook's knowledge points must be moved or deleted before the wordbook can be deleted (`knowledge_points.wordbook_rid` is required and does not cascade).

- There are no built-in decks and no category restriction: one book can hold words, grammar and names together, told apart by the knowledge point's `kind` (word / grammar / name).
- The legacy built-in decks (`n1_vocab`, `grammar_expression`, `name_reading`) are migrated into ordinary wordbooks of that user, named as the interface used to call them or as the user renamed them. Only decks that actually contain items are created.
- Legacy `wordbooks.deck` (category restriction) is removed.

#### `wordbook_stats`: wordbook statistics (read-only view, computed on demand)

No count columns are stored: adding, deleting and moving knowledge points, and every review, change the statistics, and stored counts easily drift from reality. The view computes on demand using the indexes `knowledge_points(wordbook_rid, kind)` and `review_schedules(user_id, point_rid)`; with a few hundred to a few thousand knowledge points per user, queries take milliseconds. If data grows large enough to be slow, it can become a trigger-maintained count table without changing the interface.

Full columns (including `rid`, `user_id`, timestamps, foreign keys and constraints): appendix [`wordbook_stats`](#wordbook_stats).

### Parts of speech

Japanese parts of speech are commonly classified in two ways: school grammar (Japanese national-language education, 10 parts of speech; verbs are 五段, 上一段 / 下一段, カ変, サ変) and Japanese-language education (materials for non-native learners: adjectives are い / な形容詞, verbs are groups Ⅰ / Ⅱ / Ⅲ). The two correspond one to one. Since 2010 the JLPT has not published a vocabulary list with parts of speech, and questions and preparation materials generally use the Japanese-language-education terms, so v3 uses those.

Names (places, people, etc.) are distinguished by `kind = name`, so there is no separate "固有名詞" part of speech; the kind of name (place, station, person, work title …) is recorded as a tag. Grammar knowledge points have no part of speech.

### Conjugation and the Japanese conjugation rule base

Conjugated forms (ます形, て形, 可能形 …) are no longer stored one by one; they are generated from "dictionary form + reading + part of speech" by looking up the **Japanese conjugation rule base**. The rule base consists of two global tables owned by no user (columns in the appendix: [`conjugation_forms`](#conjugation_forms), [`conjugation_rules`](#conjugation_rules)):

- `conjugation_forms`: kinds of forms. Verbs: dictionary, polite (ます形), negative (ない形), past (た形), te (て形), potential, passive, causative, causative_passive, volitional, conditional_ba, conditional_tara, imperative, prohibitive; adjectives: adverbial (副詞形), attributive (連体形), etc.
- `conjugation_rules`: one rule = part of speech + dictionary-form ending + form → the text appended after removing the ending, with an explanation of the step (translated field `step`, shown in the explanation language).

| Part of speech | Ending | Form | Append | Example | Step explanation |
|---|---|---|---|---|---|
| verb_1 | く | te | いて | 書く → 書いて | く becomes い, then add て |
| verb_1 | む | te | んで | 読む → 読んで | む becomes ん, then add で |
| verb_1 | む | polite | みます | 読む → 読みます | む becomes み, then add ます |
| verb_2 | る | negative | ない | 食べる → 食べない | drop る, add ない |
| verb_3_suru | する | potential | できる | 勉強する → 勉強できる | する becomes できる |
| i_adjective | い | past | かった | 高い → 高かった | drop い, add かった |
| verb_1 | 行く | te | 行って | 行く → 行って | Exception: the て形 of 行く is 行って |
| verb_1 | ある | negative | ない | ある → ない | Exception: the negative of ある is ない |
| i_adjective | いい | past | よかった | いい → よかった | Exception: いい conjugates with よ |

Generation uses **the longest matching ending**: 「行く」 is longer than 「く」, so 行く uses the exception rule and 書く the ordinary rule. Exceptional verbs (行く, ある, いらっしゃる・おっしゃる・なさる・くださる・ござる, 問う・請う, いい／よい, ずる verbs, etc.) are therefore just rules with longer endings; they need no extra code and no separate classification on the knowledge point. Endings are compared with both the spelling and the reading (one rule each for 「行く」 and 「いく」).

The rule-base data is compiled in phase 1 from the conjugation tables used in Japanese-language education, with tests covering every part of speech and every form.

The conjugations and steps written by AI in legacy data (`item_json.conjugations`, 38 words in production, with names mixed such as polite / ます形, te / て形 / te_form) are not migrated; during migration they are compared one by one with the rule-generated results, and mismatches are written to the migration report to find words with a wrong part of speech or group (e.g. the 五段 verb 「帰る」 labeled as 一段). The legacy tables `knowledge_forms` and `knowledge_form_steps` are not created.

### Part-of-speech conversion

Legacy `part_of_speech` is free text written by AI at entry time; the 496 production items contain about 110 different spellings (the user's local database has 30-odd more), mixing four kinds of information. Migration splits them by rules:

| Information in the legacy text | Examples | Destination |
|---|---|---|
| Main part of speech | 名詞、動詞、ナ形容詞、形容動詞（ナ形容詞）、副詞、他动词（一段动词） | `pos` (Chinese / Japanese and simplified / traditional spellings unified) |
| Transitivity, サ変 | 動詞・他動詞、名詞・サ変動詞（自動詞） | `transitivity`, `is_suru_noun` |
| Conjugation group | （ワ行五段）、下一段活用、一段; and legacy `inflection_class` (godan / ichidan / suru / kuru / i_adjective / na_adjective) | Merged into `pos` (godan → verb_1, ichidan → verb_2, suru → verb_3_suru or noun + `is_suru_noun`, kuru → verb_3_kuru); text contradicting `inflection_class` goes to the migration report |
| Other notes | 外来語、略語、四字熟語、時間名詞、副詞的用法; 地名、駅名、人名、作品名; grammar functions such as 文法・様態; colloquial phenomena such as 口語縮約・進行状態 | Tags (`knowledge_tags`) |

Spellings the rules cannot convert are listed in the migration report and migrated after manual confirmation. The entry APIs (REST, MCP) accept only enum values, not free text.

### Memory card templates

Memory cards are only for reviewing the knowledge point itself: look at the front, recall the back. A few fixed templates are offered per category, and the user chooses one each for words, grammar and names (`user_card_templates`) instead of configuring fields one by one. Templates are global data (`card_templates`, `card_template_fields`); their names and descriptions are shown in the explanation language.

| Category | Template | Front | Back | Good for |
|---|---|---|---|---|
| Word | Standard (default) | Spelling | Reading, romaji, meaning, 1 example (with translation), 1 memory point, memory image | Everyday review |
| Word | Simple | Spelling | Reading, meaning | Going through many words quickly |
| Word | Example | 1 example (without translation) | Spelling, reading, meaning, example translation | Recalling meaning in context |
| Word | Japanese definition | Spelling | Reading, Japanese definition, paraphrase, 1 example (without translation) | Understanding Japanese in Japanese; N2 and above |
| Grammar | Standard (default) | Pattern | Connection, meaning, 1 example (with translation), 1 memory point | Everyday review |

## 6. Question bank

### Unified data model: group → question → option

The 23 JLPT question types (see the [question type specifications](question-type-specifications.md)) differ in four ways: how many questions form a group and which materials they share; how the tested part is marked in the prompt; what form the options take; and whether questions can be drawn separately. v3 unifies all types into three levels, with the differences described by the global question type table `question_types` instead of a table per type:

```
question_types (type rules, global)
      │ type_id
question_groups (group / 大問)──< question_group_materials >── materials (passages, notices, images, audio)
      │                                                            └─< material_sentences (sentences and key sentences)
      └─< questions
                    ├─< question_marks (marks: tested item, blanks, ★; in the prompt or in a material text)
                    ├─< question_options (options with stable IDs)
                    ├─< question_explanation_sections (explanation sections: basis, steps, full answer, tip, objective)
                    ├─< question_evidence (evidence: a span in the prompt / material text / listening script, optionally for one option)
                    ├─< question_tags
                    └─< knowledge_point_questions >── knowledge_points (tested item / prerequisite / contrast)
```

- **Group (`question_groups`)**: a set of questions of one type sharing instructions and materials. A single vocabulary or grammar question is a group with one question. Type, status, level, instructions, scene description and option shuffling are on the group.
- **Material (`materials`)**: passages, notices or tables, images, audio. A group may use several materials, told apart by `role` (main text, passage A / B, notice, scene image, audio). Audio may be clipped (`clip_start_ms`, `clip_end_ms`).
- **Question (`questions`)**: the prompt and the question's own audio or image. Questions of all types have the same columns; there are no type-specific columns.
- **Option (`question_options`)**: stable ID, correct answer marked on the option; may be text, image or audio.

#### Question definition: the same tables for all types

| Content | Stored in | Use by question type |
|---|---|---|
| Instructions, scene | `question_groups.instruction`, `context` | All types |
| Materials | `question_group_materials` → `materials` | Reading: passage / passages A and B / notice; listening: audio, scene image; single vocabulary and grammar questions: none |
| Prompt | `questions.prompt`, `prompt_media_rid` | When only audio exists (即時応答, etc.), the prompt is audio |
| Marks | `question_marks`: `kind` + start/end + label, in the prompt or in a material text | 漢字読み, 表記, 言い換え: target (underline); 語形成, 文脈規定, 文法形式: blank; 文の組み立て: one slot per blank, the ★ blank is star_slot; 文章の文法: blank, placed in the passage text; reading, listening, 用法: no marks |

### Options and answers

Full columns in the appendix: [`question_marks`](#question_marks), [`question_options`](#question_options), [`question_explanation_sections`](#question_explanation_sections), [`question_evidence`](#question_evidence), [`question_tags`](#question_tags).

- **Options have stable IDs**: an option's `rid` is its ID and does not change with display order. `position` is the canonical order (1–4 in the official question).
- **The correct answer is marked on the option**: `is_correct` = 1, at most one per question (enforced by a unique index). The answer is not expressed as "the n-th option".
- **Client-side shuffling**: when the group's `shuffle_options` = 1, the client shuffles the options; questions whose options refer to each other (「1と2の両方」, etc.) and official questions are set to 0 and shown in `position` order.
- **An answer records only the option ID**: `attempt_answers.selected_option_rid`. Grading checks `is_correct` of the chosen option, independent of display position. The text of the chosen and correct options at answer time (`selected_text`, `correct_text`) and the result (`correct`) are also stored: later edits to the question do not change historical correctness or accuracy, and the choice is still visible after an option is deleted.
- **文の組み立て (ordering questions)**: the four fragments are the four options, and the correct answer is the fragment in the ★ blank (`is_correct`); the blanks and the ★ blank are marks on the prompt (`question_marks`), and the full sentence is written in the `full_answer` explanation section.
- **Questions whose options are read out in the audio** (即時応答, 概要理解, 発話表現 and the first two questions of listening 統合理解): the options have neither text nor a file and are shown by number only; when useful, the spoken content can be written in `text` as a transcript.
- **Positions**: `start_offset` and `end_offset` of marks and evidence are UTF-16 offsets, the same as JavaScript string indexes (`text.slice(start, end)`).

Questions and materials are edited in place without history. When reviewing past practice, the prompt and explanations show the latest content, while correctness follows what was saved at answer time. If strictly frozen papers are ever needed (formal mock exams), version tables can be introduced then.

The listening question number `library_number` is not migrated; listening questions are ordered by their new QL codes.

### Validation rules: defined per type, shared by all clients

Question types have different requirements: choice questions need a correct option and explanations; dictation has no options and its answer is a reference text; shadowing only records audio and has neither answer nor explanation; explanations of official listening questions may be omitted. Validation rules are therefore defined per question type and stored as data rather than hard-coded.

**Answer modes** (`question_types.answer_mode`)

| Answer mode | Meaning | Question types |
|---|---|---|
| `choice` | Choice with one correct option | All official types, reading basic training, sound discrimination |
| `text_input` | Text input compared with the reference answer (`questions.expected_text`); the answer record stores `attempt_answers.answer_text` | Dictation |
| `recording` | Recording, not graded; the answer record links `attempt_answers.recording_rid` | Shadowing |
| `none` | No answer or free response, not scored | Free response |

The former "listening basic training" is split into 4 types: sound discrimination `listening-basic-discrimination`, dictation `listening-basic-dictation`, shadowing `listening-basic-shadowing`, free response `listening-basic-free`.

**Validation rules** (`question_type_rules`: type × rule → required / optional / forbidden / warn only)

| Rule | Vocabulary, grammar | Reading (official) | Listening (official) | Sound discrimination | Dictation | Shadowing, free response |
|---|---|---|---|---|---|---|
| Prompt `prompt` | required | required | optional (may be audio only) | optional | optional | optional |
| Options `options` | required, 4 | required, 4 | required, 4 (即時応答 and 発話表現: 3) | required, at least 2 | forbidden | forbidden |
| Correct option `correct_option` | required | required | required | required | forbidden | forbidden |
| Reference answer `expected_text` | forbidden | forbidden | forbidden | forbidden | required | forbidden |
| Marks `marks` | by type (underline, blank, ★) | forbidden (except 文章の文法) | forbidden | forbidden | forbidden | forbidden |
| Materials `materials` | forbidden (文章の文法: required) | required | required | required | required | required |
| Basis `basis` | required | required | optional | optional | optional | forbidden |
| Option reasons `option_analysis` | required | required | optional | optional | forbidden | forbidden |
| Evidence `evidence` | — | warn only (recommended) | — | — | — | — |
| Automatic checks | distractor in knowledge points, duplicate options, option length, tested item not unique; 漢字読み also checks distractors that are another reading and the option form of reading questions | option length | option length | option length | — | — |

The complete rules of each type are the data in `question_type_rules` (26 types, 261 rules).

**All clients share one validator**

- The validator is written once in `src/domain/` (JS) and driven by the `question_type_rules` data.
- Server: runs when REST or MCP writes a question; unmet required / forbidden rules reject the write, and warn-only rules are written as review findings. The server has the final say.
- Web: the add / edit question form imports the same module and shows the same errors while editing, before submission.
- iOS: no second implementation; it calls the server's validation-only endpoint `POST /api/questions/validate` (nothing is saved).
- AI: can check with the MCP tool `validate_question` before submitting.
- Rules are delivered to clients through `GET /api/question-types`, and forms show or hide inputs by question type (e.g. no option or explanation inputs for shadowing questions).

### Question review: decided by an AI agent

Structural validation only guarantees that a question is "well-formed"; it cannot guarantee distractor quality (a distractor that is also correct, one that is absurd, clearly uneven option lengths, etc.). Every group goes through the flow below after it is created or edited, and the review verdict is decided by an AI agent itself: **passing AI review makes it ready; no learner confirmation is needed.**

```
AI authors ──▶ ① hard checks ──fail──▶ write rejected, error list returned to the authoring AI
                 │pass
                 ▼
              ② automatic checks (warnings only) ──▶ status needs_review
                 ▼
              ③ AI review (get_question_review_context → submit_question_review)
                 ├─ pass   ──▶ ready
                 ├─ revise ──▶ needs_revision ──▶ authoring AI revises ──▶ back to ①
                 └─ reject ──▶ retired
              ④ after release: answer statistics or a learner's "report a problem" ──▶ back to needs_review
```

**① Hard checks** (on write; failure rejects the write): the "required" and "forbidden" rules of `question_type_rules` for the type (see the previous section), plus for every type: option texts are distinct, evidence positions are within the source and quotes match, and the level is one the type applies to.

**② Automatic checks** (run by the server only for types whose rule is "warn only", written to `question_review_findings` with reviewer = system)

| Check | Content |
|---|---|
| `distractor_in_knowledge` | A distractor appears among the related knowledge point's alternative spellings, related words or synonym comparisons and may also be correct |
| `distractor_also_reading` | Reading questions: a distractor is another valid reading of the target word |
| `reading_options_form` | Options of reading questions are all kana; options of 表記 questions all contain kanji |
| `option_length_skew` | The correct option is clearly longer or shorter than the others |
| `duplicate_options` | Options identical to those of another question of the same knowledge point |
| `target_not_unique` | The marked tested item appears more than once in the prompt |

**③ AI review** (through MCP)

- `get_question_review_context(group)`: returns the group, materials, questions, options, explanations, the warnings from ②, and the type's review checklist (from "structural checks and content review" and "explanation template" in the [question type specifications](question-type-specifications.md)).
- The AI judges each question and each option: whether the answer is unique, whether each distractor is reasonable (tempting but definitely wrong), whether the explanation covers every option, and whether the prompt is natural.
- `submit_question_review(group, verdict, summary, findings[])`: writes `question_reviews` and `question_review_findings` and changes the group status according to the verdict.
- Review by another session or another agent is recommended rather than letting the authoring AI review its own questions; `agent_label` records the reviewer, so an agent reviewing its own questions is visible in the review log.
- When revision is needed, the authoring AI gets the questions and review comments with `list_questions_needing_revision`, revises and resubmits; findings fixed by the revision are marked `resolved`.

**④ Feedback after release**

- Answer statistics: a distractor nobody ever chooses (too weak), or one chosen more often than the correct answer (possibly ambiguous), automatically produces a warning and returns the group to needs_review.
- A learner's "report a problem" during practice: recorded as a review with reviewer = user, and the group returns to needs_review.

Migrated questions: questions used in practice start as ready, and the AI reviews all groups once after migration; questions in drafts are draft.

### De-duplication

Migration de-duplicates by **question type + prompt**:

1. Every copy of a question in legacy data (knowledge point questions, draft questions, practice questions, snapshots, reading and listening questions) gets its official question type `type_id`, and the prompt is normalized (trim whitespace, unify full-width / half-width characters and line breaks).
2. Copies with the same type and the same normalized prompt are treated as one question; only one question (and its group) is created.
3. When copies of one question differ in options, answer or explanation, the most recently modified copy becomes the question's content; differences of the other copies go to the migration report for manual confirmation.
4. Reading and listening questions with the same prompt but different materials (passage, audio) are not merged. Migration groups reading and listening questions by passage / audio, so questions of the same passage form one group; other questions form one group each.
5. The temporary mapping table records the new question of every legacy copy, and legacy answers, practice sets and drafts are linked to the new questions through it. Legacy answers are text and are matched to the new question's option IDs by text; those that do not match (from copies with different content) have an empty `selected_option_rid` and keep the text and correctness of the time. Merges are written to the migration report.

## 10a. Query patterns and Cloudflare limits

Limits of Cloudflare Workers (Durable Object SQLite): at most 100 bound parameters per statement, expression depth at most 100, at most 100 KB per statement, and a cap on compound SELECTs. The data layer follows these rules:

1. **Pass IDs or multiple lookup keys as a single JSON parameter** and expand it in SQL with `json_each(?)`; never write `IN (?, ?, …)`. The number of parameters does not depend on the number of rows.
2. **Query by table in batches, not row by row**: a detail page = 1 query on the main table + 1 per child table + 1 for all translations; a list page = 1 SQL statement (translations picked along the language fallback chain with a window function).
3. **SQL returns flat rows and JSON is assembled in JS**; whole records are not built in SQL with nested `json_object` (v2 exceeded the expression depth limit that way).
4. **No UNION to combine data**; each source is queried separately.
5. **Bulk writes use `INSERT … SELECT … FROM json_each(?)`**, one JSON parameter per statement.

Measured (copy of production data, local SQLite):

| Scenario | Parameters | Time |
|---|---|---|
| Word list: 496 items + meanings picked by language fallback, one SQL statement | 2 | 2.6 ms |
| Knowledge point detail: all translations of W5 and 10 child rows, one SQL statement | 2 | 0.03 ms |
| Full sync: all 24,306 translations | 0 | 29 ms |

Looking up translations by `(owner_table, owner_rid)` uses the primary key index. The Durable Object's SQLite runs in the same process as the code with no network round trip, so the ~8 small queries of a detail page take under 1 ms in total.

## 12. Confirmed decisions (2026-10-09)

1. **Legacy furigana data** (`ruby_terms`, `japanese_annotations`): dropped. The migration report lists text that had furigana; the AI checks it later and annotates with on-demand furigana (`ruby_annotations`) where needed. Currently there is data of only one user.
2. **Global sample data `review_items`**: not migrated; no sample data is offered any more.
3. **Legacy counters of review progress** (`correct` / `wrong`, `count_semantics`): dropped.
4. **Question de-duplication**: by question type + prompt; rules in "De-duplication" in §6.
5. **"N2関連", "N3関連"**: marked directly as the corresponding level (N2関連 → `jlpt_level_min` = `jlpt_level_max` = N2). "非JLPT核心词" and "生活词汇" still become tags.
6. **Knowledge point category `kind`**: only three categories: word (including phrases, idioms and phrase sets), grammar (including colloquial sound-change rules) and name. Code prefixes W / G / N. Finer legacy `type` values (phrase, listening_rule, etc.) become tags.
7. **Kinds of names** (places, stations, people, work titles …): tags; no "固有名詞" part of speech.
8. **Conjugation step explanations**: unified as rules by part of speech and ending, kept in the global Japanese conjugation rule base ("Conjugation and the Japanese conjugation rule base" in §5).
9. **Questions have no versions**: questions and materials are edited in place; options have stable IDs, the correct answer is marked on the option, clients may shuffle, and answers record only option IDs plus the text and correctness of the time ("Options and answers" in §6).
10. **Unified data model**: all question types use "group → question → option" with the same marks and explanation structure (§6).
11. **Memory cards use templates**: fixed templates per category, and users only choose a template; other practice belongs to question practice (random practice, AI-customized practice) ("Memory card templates" in §5).
12. **Validation rules are defined per question type**: rules are stored as data (`question_type_rules`), and the server, MCP, Web and iOS share one validator ("Validation rules" in §6).
13. **Question review is decided by an AI agent**: passing AI review makes a question ready without learner confirmation ("Question review" in §6).
